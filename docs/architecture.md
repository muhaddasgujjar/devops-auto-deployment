# Architecture decisions

Derived from the assessment in the referenced 'Analyze DevOps project and plan'
chat and its 19 October 2026 build plan. This repository implements the initial
delivery-loop foundation, not the eight-week product in one milestone.

## Ownership

1. A trusted main-branch Jenkins job tests, builds, scans, and publishes an image.
2. The job resolves the registry digest and commits constrained YAML to a separate
   environment repository. A failed test/scan cannot update desired state.
3. Argo CD synchronizes the environment directory into `demo-dev`.
4. Argo Rollouts owns service revision selectors and candidate analysis.
5. Prometheus discovers pods and attaches each pod's Rollouts hash as `revision`.

Jenkins holds no kubeconfig. Argo CD ignores only the service selector field owned
by Rollouts. The environment application is restricted to the demo namespace and
three resource kinds. Namespace creation is a bootstrap responsibility.

## First experiment

Keep stable and preview services, two replicas, 120 seconds of old-revision
retention, and pre-promotion analysis. Candidate requests are generated by an
external client against preview. Analysis requires at least 100 requests in a
rolling 60-second window and healthy scrape targets. It checks 5xx <= 5% and
p95 latency <= 500ms in five measurements spaced 15 seconds apart.

One failed measurement aborts this initial conservative policy. Empty/NaN data
meets neither success nor failure: repeated inconclusive results pause progression.
Prometheus transport/query errors reach an error limit and cannot promote.
This refines the assessment's proposed three-failure policy; tuning needs trials.
The policy is not a latency SLO or a demonstrated false-positive bound.

Readiness timeout requests `progressDeadlineAbort`. Live testing found that
retained, scaled-down ReplicaSets with stale scale-down markers can suppress
deadline handling in the selected controller. The lab now sets
`revisionHistoryLimit: 0` to remove retired sets, and exports evidence before
subsequent trials clean up their in-cluster history. Active stable/candidate sets
and the configured running-replica retention window remain under Rollouts control.
This trades Kubernetes historical objects for archived lab evidence; a production
observer must persist results before cleanup. See live validation for the retest.

The first deployment has no prior stable revision to restore. Argo can skip pre-promotion analysis on initial
creation: establish and independently verify a healthy baseline first.

The original milestone covered rejection before traffic switched. The local
policy now adds serving-only post-promotion analysis and 600-second retention.
Rollouts returns traffic after a failed post gate; a bounded observer commits
the prior verified desired state to Git and verifies recovery before releasing
the durable publication lease. Failed Git writes/timeouts require an explicit
retry. See [post-promotion acceptance](post-promotion.md). Stable dependency
failures that also affect the fallback, indefinite monitoring and host loss
remain distinct limits; no release may be called recovered without live proof.
Pre-promotion metrics now require both expected targets with samples no older
than 15 seconds; this addresses missing-target completeness for the fixed lab replica count.

## Resource profile and limits

The inspected Windows host has 8,425,529,344 bytes of RAM, eight logical processors,
and roughly 79 GiB free disk. Initially, no Docker, k3d, kubectl, Helm, or usable Linux WSL
distribution was detected. Ubuntu 24.04, Docker Engine, k3d, kubectl, and Trivy
were subsequently installed; Helm is not required by this lean profile.
k3d supplies k3s in Docker for a disposable single-host
lab; it is not the proposed multi-VM resilience experiment or production HA.

Use a Linux build machine separate from the cluster for privileged Docker builds.
The registry is loopback-bound HTTP for the local lab only. A remote CI agent
needs a mutually reachable TLS registry and matching Kubernetes pull credentials.
Prometheus now uses a retained local PVC with bounded sample retention. Release
evidence has a separate SQLite catalogue and SHA-256 object store outside the
checkout. See [persistence and restore verification](persistence.md) for scope and
single-host limitations. No GitHub webhook is assumed to reach localhost.
